## 1. Aporte realizado

Durante esta etapa participé en la implementación física de la base de datos del Sistema de Gestión Comercial y Control de Inventario para Joyería utilizando Microsoft SQL Server.

Mi aporte principal consistió en desarrollar los scripts DDL y DML correspondientes a las tablas `Rol` y `Usuario`.

En el script DDL definí las tablas, sus atributos, tipos de datos, claves primarias, clave foránea y restricciones de integridad. En el script DML incorporé registros coherentes para comprobar el funcionamiento de ambas tablas.

Inicialmente también implementé la tabla `Consulta`, debido a que formaba parte de una versión anterior del modelo. Luego de una revisión grupal, se decidió eliminarla del diseño definitivo. A partir de esta decisión adapté los scripts, los datos de prueba y la documentación para que coincidieran con el nuevo modelo relacional.

También realicé pruebas en SQL Server y participé en la organización y carga de los archivos correspondientes a la Etapa III en el repositorio del equipo.

## 2. Decisiones en las que participé

Participé en las siguientes decisiones relacionadas con las tablas asignadas:

- Establecer una relación 1:N entre `Rol` y `Usuario`.
- Utilizar identificadores automáticos mediante `IDENTITY`.
- Definir `IdRol` como clave foránea de `Usuario`.
- Impedir la eliminación de un rol que se encuentre asociado a usuarios.
- Establecer el nombre de cada rol como un valor único.
- Establecer el DNI, el nombre de usuario y el email como valores únicos.
- Incorporar el email para cumplir con la regla de negocio que exige un correo único para cada usuario registrado.
- Definir los estados `Activo` e `Inactivo` como únicos valores permitidos para un usuario.
- Utilizar `Activo` como estado predeterminado.
- Utilizar nombres de atributos sin caracteres especiales, como `Contrasenia`.
- Eliminar la tabla `Consulta` para adaptar la implementación al modelo definitivo acordado por el grupo.

También participé en la revisión de los roles necesarios para distinguir los diferentes tipos de usuarios del sistema.

## 3. Problemas o dificultades identificadas

Una de las principales dificultades fue que el modelo relacional fue modificado mientras se desarrollaban los scripts de implementación. La primera versión incluía la tabla `Consulta`, pero posteriormente el grupo decidió retirarla del modelo definitivo.

También fue necesario revisar la nomenclatura utilizada por los diferentes integrantes, debido a que algunos scripts utilizaban nombres con guion bajo y otros empleaban PascalCase.

Otra dificultad fue determinar los atributos y restricciones necesarios para `Usuario`, especialmente los campos que debían ser únicos y los valores permitidos para su estado.

Además, se detectó que el modelo actualizado no mostraba el atributo `Email`, aunque la regla de negocio RN.01 exige que el correo electrónico de cada usuario sea único.

## 4. Soluciones o propuestas realizadas

Para resolver las diferencias entre versiones, adapté mi implementación para conservar únicamente las tablas `Rol` y `Usuario`, de acuerdo con el modelo definitivo acordado por el equipo.

Propuse incorporar el atributo `Email` en `Usuario` con las restricciones `NOT NULL` y `UNIQUE`, con el objetivo de mantener la correspondencia entre la implementación y las reglas de negocio de la Etapa I.

También unifiqué la nomenclatura de las tablas, atributos y restricciones con la utilizada por el resto del equipo. Los archivos fueron renombrados para reflejar con mayor claridad su contenido.

En Microsoft SQL Server verifiqué la creación de las tablas, la relación entre `Rol` y `Usuario`, la inserción de los datos de prueba y la cantidad de registros cargados mediante consultas `SELECT` y `COUNT`.

La evolución del modelo quedó documentada en los commits del repositorio, conservando la primera implementación y agregando posteriormente las correcciones surgidas de la revisión grupal.
