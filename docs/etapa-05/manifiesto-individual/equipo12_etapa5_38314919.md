## Aporte realizado
Durante esta etapa participé en el desarrollo de la Etapa V del Sistema de Gestión Comercial y Control de Inventario para Joyería ALBA utilizando Microsoft SQL Server. Mi aporte principal consistió en implementar y probar las soluciones de Seguridad de Usuarios/Roles y la Optimización del Rendimiento mediante Índices.
Para cumplir con las consignas solicitadas por la cátedra, desarrollé:
1.	Gestión de Permisos y Roles de Seguridad:
•	Creé los usuarios para la base de datos y configuré un rol con permisos de solo lectura sobre la tabla de productos.
•	Asigné dicho rol a un usuario específico y dejé a otro usuario sin ese perfil para comprobar cómo responde el sistema en ambos casos.
•	Comprobé cómo un usuario de solo lectura no puede modificar directamente la tabla de productos mediante sentencias directas, pero sí puede registrar información utilizando los procedimientos almacenados autorizados por el equipo.

2.	Prueba de Optimización mediante Índices:
•	Automaticé mediante un script la carga masiva de 1.000.000 de registros de ventas con campos de fecha e importe para simular un volumen real de operaciones de la joyería.
•	Realicé búsquedas por períodos de fechas sin índices en la tabla, registrando los tiempos de espera y el esfuerzo realizado por el motor de la base de datos.
•	Creé un índice agrupado sobre la columna de fecha y repetí la consulta para comparar el cambio en la velocidad de respuesta.
•	Eliminé el primer índice y creé uno nuevo que incluía además las columnas consultadas (índice con cobertura), midiendo la mejora final en la agilidad de los reportes.


## Decisiones en las que participé
Participé en las siguientes decisiones del equipo:
	Estrategia de Permisos por Roles: Organizar los permisos agrupándolos en roles en lugar de asignarlos usuario por usuario, para facilitar el control cuando ingresen nuevos empleados al negocio.
	Control a través de Procedimientos: Permitir que los usuarios con perfil de lectura puedan guardar datos únicamente mediante procedimientos almacenados, protegiendo las tablas contra cambios directos no autorizados.
	Elección de la Tabla para la Carga Masiva: Generar una tabla de ventas históricas con un millón de filas para que las pruebas de rendimiento con índices muestren diferencias de velocidad reales y notorias.
	Estructura del Índice con Cobertura: Incluir en el índice de búsqueda la columna del monto cobrado para que la base de datos encuentre toda la información necesaria de una sola vez, sin tener que hacer lecturas adicionales.
Estas decisiones fueron consultadas y provadas, con el equipo para asegurar que las pruebas reflejen situaciones reales de la joyería.

## Problemas o dificultades identificadas

Entender la diferencia entre Logins y Usuarios: Al principio fue confuso diferenciar el acceso general al servidor SQL Server de los permisos específicos dentro de la base de datos de la joyería.
Tiempos en la Carga de Datos: Insertar un millón de registros de forma manual tomaba demasiado tiempo, por lo que fue necesario buscar una forma de automatizar el proceso en un solo paso.
Comprender la diferencia de lectura: En la parte de optimización, entender qué significaba que la base de datos leyera toda la tabla completa en lugar de ir directamente al dato buscado.
Soluciones o propuestas realizadas
Uso de Roles y Pruebas de Acceso: Se definieron usuarios específicos de prueba (usuario_con_rol y usuario_sin_rol) para validar visualmente que el sistema rechaza los accesos no autorizados y permite consultar solo a quienes tienen el permiso asignado.
Automatización del Script de Carga: Se utilizó una consulta combinada para generar el millón de filas en pocos segundos, asignando fechas y montos aleatorios. 
Uso de Índices para Acelerar la Consulta: La creación del índice sobre la fecha de venta permitió transformar la búsqueda: en lugar de revisar el millón de registros uno por uno, la base de datos pasó a buscar directamente en el rango de fechas solicitado, reduciendo drásticamente el tiempo de respuesta.
