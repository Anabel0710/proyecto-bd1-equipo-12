## 1. Aporte realizado
En esta etapa me encargué del módulo de **Transacciones y Transacciones Anidadas** en SQL Server para la base de datos de la joyería[cite: 11]:
- Diseñé y escribí el script SQL con los bloques `BEGIN TRANSACTION`, `COMMIT`, `ROLLBACK` y el manejo de errores con `TRY...CATCH`.
- Realicé las tres pruebas prácticas requeridas por la cátedra:
  1. Caso de éxito: registro de una venta completa (`Comprobante`, `DetalleComprobante` y descuento de stock en `Producto`).
  2. Caso de fallo intencional: inserción de un producto inexistente para forzar el error por clave foránea y comprobar que el `ROLLBACK` deshace la operación sin dejar registros a medias[cite: 11].
  3. Transacción anidada: venta principal con un subproceso interno en `AjusteStock`, controlando los niveles del contador `@@TRANCOUNT`[cite: 11].
- Capturé las pantallas con los resultados en SSMS, organicé la carpeta de imágenes del equipo y redacté el informe técnico explicativo en Markdown[cite: 11].

## 2. Decisiones en las que participé
- **Selección del circuito de negocio:** Acordamos con el equipo modelar la venta de mostrador de una joya (Anillo Solitario de Plata) afectando tres tablas consecutivas para cumplir con la consigna de operaciones compuestas.
- **Estructura compartida en el repositorio:** Definimos crear una carpeta general `img/` dentro de `docs/etapa-05/` y subcarpetas temáticas (como `Transacciones/`, `Triggers/`, `Seguridad/`) para que cada integrante suba sus evidencias sin pisar los archivos de las demás[cite: 11].
- **Criterio de reversión ante errores:** Decidimos que ante cualquier fallo en una transacción anidada, el `ROLLBACK` anule todo el paquete completo (tanto la venta como el ajuste logístico) para no comprometer el balance contable ni el inventario.

## 3. Problemas o dificultades identificadas
- Al probar la transacción con fallo provocado, costaba visualizar con claridad si el registro de la cabecera realmente se eliminaba o si quedaba flotando en la tabla.
- Entender el comportamiento real de las transacciones anidadas en SQL Server: al principio creía que un `COMMIT` interno ya guardaba los datos en disco, pero en realidad solo restaba un nivel en el contador.
- En GitHub me encontré con la dificultad de organizar las carpetas de imágenes sin que se agrupen visualmente de manera confusa (`img/Transacciones`), y coordinar la subida para no generar commits innecesarios en el historial.

## 4. Soluciones o propuestas realizadas
- Realicé consultas con `COUNT(*)` sobre la tabla `Comprobante` y consultas de stock antes y después de provocar el error, logrando comprobar de forma visual que la base de datos volvía exactamente al estado inicial.
- Agregué mensajes de seguimiento en consola con `PRINT '@@TRANCOUNT = ' + CAST(@@TRANCOUNT AS VARCHAR)` en cada paso del script anidado, lo que me permitió comprobar cómo el contador sube (1 y 2) y baja secuencialmente (1 y 0) hasta la confirmación final.
- Creé un archivo de control (`.gitkeep`) para fijar la carpeta principal `img/` y luego subí la subcarpeta `Transacciones/` completa, manteniendo la estructura limpia para el resto de mis compañeras.
